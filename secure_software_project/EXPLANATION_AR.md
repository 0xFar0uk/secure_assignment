# شرح المشروع بالعربي المصري - Student Portal

## 1) التطبيق بيعمل إيه؟

ده برنامج Console بسيط لإدارة حساب طالب. المستخدم يقدر يعمل Register، وبعدها Login، ويعرض بيانات بروفايله باستخدام Student ID. استخدمنا `LinkedList` لتخزين الحسابات والبروفايلات أثناء التشغيل. البيانات بتتمسح لما تقفل البرنامج؛ مفيش Database في النسخة التعليمية دي.

عندنا نسختين:
- `src-vulnerable`: فيها 3 ثغرات مقصودة علشان نحللها ونثبت تأثيرها.
- `src-secure`: نفس فكرة التطبيق بعد إصلاح الثغرات الثلاثة.

> مهم: أسماء الـ techniques في الصورة هي طرق تحليل واختبار، مش أنواع ثغرات. اخترنا Static Analysis وSymbolic Execution وDebugging. أما الثغرات الثلاثة نفسها فهي Hardcoded Credentials، وAuthentication Logic Flaw، وIDOR/Broken Access Control.

## 2) تشغيل المشروع

لازم JDK 17 أو أحدث. افتح Terminal جوه فولدر النسخة المطلوب تشغيلها:

```bash
javac *.java
java StudentPortalApp
```

شغّل كل نسخة من فولدرها لوحده؛ لأن النسختين فيهم class بنفس الاسم. مفيش مكتبات خارجية محتاج تنزلها.

## 3) شرح الملفات والكلاسات

### `PasswordHasher.java`

- `SALT_LENGTH_BYTES`: طول الـ salt العشوائي، والـ salt بيخلي نفس كلمة السر تنتج hash مختلف لكل حساب.
- `ITERATIONS`: عدد جولات PBKDF2. زيادة الجولات بتخلي تجربة كلمات سر كتير أبطأ على المهاجم.
- `KEY_LENGTH_BITS`: طول قيمة الـ hash الناتجة.
- `SecureRandom`: بيولّد salt عشوائي قوي.
- `generateSalt()`: بيولّد bytes عشوائية وبعدها يحولها إلى Base64 علشان نخزنها كنص.
- `hashPassword()`: بياخد كلمة السر والـ salt، ويستخدم `PBKDF2WithHmacSHA256` لإنتاج hash؛ مش بيخزن كلمة السر نفسها.
- `PBEKeySpec`: بيجهز كلمة السر والـ salt وعدد الجولات وطول الناتج.
- `spec.clearPassword()`: بيمسح النسخة المؤقتة من كلمة السر الموجودة جوه الـ spec بعد الانتهاء.
- `verifyPassword()`: بيحسب hash لكلمة السر المدخلة ويقارنه بالـ hash المخزن باستخدام `MessageDigest.isEqual`.

### `UserAccount.java`

- المتغيرات `username` و`salt` و`passwordHash` محفوظة كـ `private final`؛ ده تطبيق للـ Encapsulation ومنع تعديل بيانات الحساب مباشرة.
- الـ constructor معمول `private` علشان إنشاء الحسابات يمر من خلال method واضحة بدل ما أي كود ينشئ كائن ناقص البيانات.
- `register()`: ينشئ salt، يحسب hash، ويرجع كائن `UserAccount`.
- `getUsername()`: يرجّع اسم المستخدم من غير ما يكشف كلمة السر أو الـ hash.
- `passwordMatches()`: يستخدم `PasswordHasher` للتحقق من كلمة السر وقت تسجيل الدخول.
- في النسخة الضعيفة فقط، `createAdminSession()` بتنشئ جلسة Admin من غير حساب مخزن. ده معمول علشان فرع الـ hardcoded credential يشتغل في التجربة؛ اتحذف من النسخة الآمنة.

### `StudentProfile.java`

- `studentId`: المعرّف اللي المستخدم بيدخله لطلب البروفايل.
- `ownerUsername`: اسم الحساب المالك للبروفايل. ده أساسي علشان نتحقق من الصلاحية، لكنه مش لازم يظهر للمستخدم.
- `fullName` و`department`: البيانات اللي التطبيق بيعرضها.
- الـ constructor بيخزن القيم عند إنشاء البروفايل.
- `getStudentId()` و`getOwnerUsername()`: بتدي كود التطبيق البيانات اللي يحتاجها للتحقق والبحث.
- `toDisplayString()`: بتنسق البيانات اللي هتظهر للمستخدم. مش بتعرض `ownerUsername`.

### `StudentPortalApp.java`

- `Scanner`: لقراءة المدخلات من الـ Console.
- `LinkedList<UserAccount> users`: قائمة الحسابات؛ كل عنصر كائن `UserAccount`.
- `LinkedList<StudentProfile> studentProfiles`: قائمة بروفايلات الطلبة.
- `nextStudentNumber`: بيخلّي كل بروفايل ياخد ID مختلف، زي `S1001` وبعده `S1002`.
- `main()`: نقطة بداية البرنامج وبتنشئ object من `StudentPortalApp`.
- `run()`: حلقة القائمة الرئيسية؛ بتفضل شغالة لحد ما المستخدم يختار Exit.
- `registerStudent()`: بياخد البيانات، يمنع اسم مستخدم مكرر أو بيانات فاضية، يختبر قوة كلمة السر، ثم يضيف الحساب والبروفايل للقائمتين.
- `logIn()`: يقرأ اسم المستخدم وكلمة السر، ينادي `authenticate()`، ويفتح الـ dashboard لو التحقق نجح.
- `authenticate()`: أهم جزء في ثغرتي بيانات الدخول. قارِن النسخة الضعيفة بالنسخة الآمنة تحت.
- `showDashboard()`: قائمة بعد تسجيل الدخول تعرض اختيار عرض بروفايل أو Logout.
- `viewStudentProfile()`: تبحث عن البروفايل باستخدام الـ ID. النسخة الضعيفة بتعرضه مباشرة؛ النسخة الآمنة بتقارن مالك البروفايل باسم المستخدم الحالي.
- `findUser()` و`findStudentById()`: بيلفّوا على الـ LinkedList عنصر عنصر؛ ده بحث خطي O(n)، مناسب لمشروع صغير تعليمي.
- `hasStrongPassword()`: Regex بتطلب 10 حروف على الأقل، وحرف صغير وكبير ورقم ورمز.
- `readLine()`: بتقلل تكرار كود طباعة السؤال وقراءة الإجابة.

## 4) الثغرات الثلاثة وإزاي نثبتها

### VULN-1 — Hardcoded Admin Credential

**المكان:** `src-vulnerable/StudentPortalApp.java` داخل `authenticate()`.

الشرط بيقارن المدخلات بالقيم الثابتة `admin` و`Admin@123` الموجودة في السورس. أي شخص يقرأ الكود يعرف بيانات الدخول؛ ده خطر لأن السر مش المفروض يكون جزء ثابت من البرنامج.

**Technique:** Static Analysis. افتح الكود واعمل Search عن `Admin@123` وعن شروط الدخول الثابتة. ممكن كمان تستخدم IDE inspection أو أداة تحليل ساكن لو متاحة.

**الاختبار:** شغّل النسخة الضعيفة، اختار Login، وأدخل `admin` ثم `Admin@123`. هتظهر رسالة نجاح ودور ADMIN. كرر نفس الاختبار في النسخة الآمنة؛ هيفشل لأن مسار الدخول الخاص ده اتحذف.

**الإصلاح:** حذف بيانات الدخول الثابتة وإزالة إنشاء Admin session من الكود. في نظام حقيقي، حسابات الإدارة تتجهز من إعدادات/إدارة سرية آمنة، مش من كلمة مرور ثابتة في source code.

### VULN-2 — Authentication Logic Flaw

**المكان:** `authenticate()` في النسخة الضعيفة:

```java
if (!account.getUsername().equals(username) && !account.passwordMatches(password)) {
    return null;
}
```

**المشكلة:** إحنا بالفعل وصلنا للحساب من `findUser(username)`، فاسم المستخدم في الحساب هو نفس المدخل. بالتالي أول جزء `!account.getUsername().equals(username)` بيكون `false`. والـ `false && أي حاجة` نتيجتها `false`، عشان كده البرنامج مش بيرفض كلمة السر الغلط.

**Technique:** Symbolic Execution (تحليل شروط المسارات).

| الرمز | المعنى | النتيجة لحساب موجود وكلمة سر غلط |
|---|---|---|
| A | `!account.getUsername().equals(username)` | `false` |
| B | `!account.passwordMatches(password)` | `true` |
| A AND B | شرط الرفض | `false` |

بما إن شرط الرفض طلع `false`، التنفيذ يكمل ويرجع الحساب؛ يبقى تسجيل الدخول ينجح رغم كلمة السر الغلط.

**الاختبار:** سجّل حساب `alice` بكلمة مرور `Alice@2026!`، اعمل Logout، وبعدها حاول الدخول باسم `alice` وكلمة مرور `wrong-password`. النسخة الضعيفة هتدخل؛ الآمنة هترفض.

**الإصلاح:** استخدام شرط رفض واضح: `if (account == null || !account.passwordMatches(password)) return null;` بمعنى ارفض لو الحساب مش موجود **أو** كلمة السر مش صحيحة.

### VULN-3 — IDOR / Broken Access Control

**المكان:** `viewStudentProfile()` في النسخة الضعيفة.

الكود بيبحث عن البروفايل بالـ Student ID وبعدها بيعرضه، من غير ما يقارن `profile.getOwnerUsername()` بالمستخدم الحالي. فمعرفة أو تخمين ID شخص آخر تكفي لعرض بياناته.

**Technique:** Debugging. حط breakpoint بعد `findStudentById(studentId)` وراقب `currentUser.getUsername()` و`profile.getOwnerUsername()`. في النسخة الضعيفة هتلاحظ اختلاف المالك عن المستخدم، ومع ذلك الكود بيكمل للعرض.

**الاختبار:** في نفس التشغيل، سجّل Alice ثم Bob. غالبًا هياخدوا `S1001` و`S1002`. سجّل دخول Alice واطلب `S1002`. النسخة الضعيفة تعرض بيانات Bob؛ الآمنة تطبع Access denied.

**الإصلاح:** قبل عرض البيانات، لازم يحصل تحقق صلاحيات: لو مالك البروفايل مختلف عن المستخدم الحالي، ارفض الطلب.

## 5) ليه استخدمنا OOP وLinkedList؟

- **OOP:** كل كلاس له مسؤولية: `UserAccount` للحساب، `StudentProfile` للبروفايل، `PasswordHasher` لمعالجة كلمات السر، و`StudentPortalApp` لتدفق التطبيق.
- **Encapsulation:** البيانات داخل الكلاسات `private`، والتعامل بيكون عن طريق methods.
- **LinkedList:** مطلوبة في التكليف، وبتوضح تخزين objects والبحث فيها باستخدام loops. البحث هنا O(n)، وده كفاية لبيانات قليلة في مشروع تعليمي؛ لو المشروع كبر، ممكن نستخدم `HashMap` للبحث الأسرع مع الحفاظ على بنية مناسبة.
- **Password hashing:** استخدمنا PBKDF2 وsalt بدل تخزين كلمة السر plaintext؛ ده إجراء أمان إضافي ومش واحد من الثغرات المقصودة.

## 6) خطوات المقارنة والتقرير

1. شغّل النسخة الضعيفة وصوّر الكود الخاص بكل ثغرة والنتيجة اللي تثبتها.
2. طبّق Static Analysis على موضع السر الثابت وشروط الدخول.
3. وثّق جدول الـ path condition الخاص بـ Symbolic Execution.
4. استخدم Debugger عند البحث عن البروفايل وراقب المالك والمستخدم الحالي.
5. شغّل نفس الاختبارات على النسخة الآمنة، وصوّر رفض الدخول بكلمة سر خاطئة ورفض قراءة بروفايل شخص آخر.
6. املأ أسماء وأرقام أعضاء الفريق في التقرير، ووزّع الأدوار حسب الأشخاص الفعليين.

**تنبيه:** التطبيق مختبري محلي وبسيط، ومش نظام جامعي حقيقي: الحسابات والبروفايلات في الذاكرة فقط، ومافيش قاعدة بيانات أو جلسات عبر الشبكة أو إدارة إنتاجية للأدوار.
