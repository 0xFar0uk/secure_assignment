# شرح الكود بالتفصيل - Line-by-Line Guide (Egyptian Arabic)

الشرح ده مطابق لأرقام الأسطر في `src-vulnerable/`. النسخة الآمنة فيها نفس التصميم تقريبًا، لكن فيها تعديلات موضّحة في آخر الملف. أرقام الأسطر ممكن تختلف بين النسختين بسبب حذف بعض أسطر الـ admin.

## 4. `StudentPortalApp.java` - شرح النسخة الضعيفة

### الأسطر 1-12: بداية البرنامج وتخزين البيانات

- **1-2:** استيراد `LinkedList` لتخزين العناصر و`Scanner` لقراءة مدخلات المستخدم.
- **4:** تعريف كلاس التطبيق الرئيسي.
- **5:** `Scanner` واحد لقراءة المدخلات من لوحة المفاتيح.
- **6:** `LinkedList<UserAccount>` فيها حسابات المستخدمين. النوع بين الأقواس معناه إن القائمة تخزن كائنات `UserAccount`.
- **7:** `LinkedList<StudentProfile>` فيها بروفايلات الطلبة.
- **8:** يبدأ ترقيم الطلبة من 1001 عشان أول ID يبقى `S1001`.
- **10-12:** `main()` هي نقطة بداية Java، وتنشئ object من التطبيق وتشغّل `run()`.

### الأسطر 14-38: القائمة الرئيسية

- **15:** `running` بتحدد إذا كانت الحلقة ما زالت شغالة.
- **16-37:** حلقة `while` تكرر القائمة لحد ما المستخدم يختار Exit.
- **17-20:** عرض اسم التطبيق وثلاثة اختيارات: تسجيل حساب، دخول، خروج.
- **21:** قراءة الاختيار ثم `trim()` لإزالة المسافات من البداية والنهاية.
- **23-36:** `switch` تنفذ الوظيفة حسب الاختيار. `break` تمنع الانتقال إلى الحالة التالية. الاختيار الغلط يظهر رسالة خطأ.
- **30-33:** اختيار `3` يغيّر `running` إلى `false`، وبالتالي تتوقف الحلقة بعد نهاية الدورة الحالية.

### الأسطر 40-65: تسجيل حساب طالب

- **41:** عنوان جزء التسجيل.
- **42:** قراءة اسم المستخدم وإزالة المسافات من أطرافه.
- **43-46:** رفض الاسم لو فاضي أو مستخدم من قبل. `findUser()` ترجع حسابًا عند وجود الاسم، و`return` يخرج من التسجيل فورًا.
- **48-52:** قراءة كلمة السر ثم اختبارها. لو مش مطابقة للسياسة، التسجيل يتوقف. الـ regex في `hasStrongPassword()` يطلب 10 أحرف على الأقل وحرفًا كبيرًا وصغيرًا ورقمًا ورمزًا.
- **54-55:** قراءة الاسم الكامل والقسم.
- **56-59:** منع البيانات الفارغة.
- **61:** إنشاء حساب فيه salt وhash وإضافته إلى قائمة الحسابات.
- **62:** إنشاء Student ID، مثل `S1001`، وبعدها زيادة العداد للطالب التالي. `%04d` تعرض الرقم بأربع خانات على الأقل.
- **63:** إنشاء كائن `StudentProfile` وربطه باسم المستخدم، ثم إضافته إلى قائمة البروفايلات.
- **64:** عرض الـ ID الجديد للمستخدم حتى يقدر يختبر عرض بروفايله.

### الأسطر 67-81: تسجيل الدخول

- **68:** طباعة عنوان Login.
- **69-70:** قراءة اسم المستخدم وكلمة السر.
- **71:** تمرير المدخلات إلى `authenticate()`.
- **73-76:** لو النتيجة `null`، يعني الدخول مرفوض؛ نعرض رسالة ونخرج من `logIn()`.
- **78-79:** عرض رسالة الدخول الناجح واسم المستخدم والدور في النسخة الضعيفة.
- **80:** تمرير الحساب الحالي إلى لوحة المستخدم. وجود `currentUser` مهم لأن أي قرار صلاحيات لازم يعتمد على الحساب الذي سجّل الدخول.

### الأسطر 83-99: `authenticate()` والثغرتان الأولى والثانية

- **83:** الدالة تستقبل username وpassword، وترجع الحساب لو قبلت الدخول أو `null` لو رفضته.
- **84-87 - VULN-1:** الشرط يقارن المدخلات بقيم ثابتة في الكود: `admin` و`Admin@123`. أي شخص يقرأ السورس يقدر يعرف بيانات الدخول. عند التطابق، تتنشأ جلسة Admin مباشرة.
- **89:** لو بيانات الدخول ليست بيانات الـ admin الثابتة، ابحث عن الحساب المسجل باسم المستخدم.
- **90-92:** لو الحساب غير موجود، ارفض الدخول.
- **94-98 - VULN-2:** الشرط يستخدم `&&` بين فشل مطابقة اسم المستخدم وفشل كلمة السر. لكن الحساب تم اختياره بالفعل باستخدام نفس اسم المستخدم، فـ `!account.getUsername().equals(username)` تساوي `false`. وبذلك `false && true` تساوي `false`، فلا يدخل البرنامج إلى `return null` وتُقبل كلمة السر الغلط.
- **98:** يرجع الحساب، فيكمل البرنامج كأن الدخول صحيح.

### الأسطر 101-120: لوحة المستخدم

- **102:** يبدأ المستخدم بحالة Logged In.
- **103-119:** حلقة تعرض القائمة لحد ما يختار Logout.
- **104-107:** عرض الاختيارات وقراءة اختيار المستخدم.
- **108-118:** الاختيار `1` يستدعي عرض البروفايل ويمرر الحساب الحالي؛ الاختيار `2` يوقف الحلقة ويسجل الخروج؛ الاختيار الغلط يظهر رسالة.

### الأسطر 122-132: عرض بروفايل الطالب والثغرة الثالثة

- **123:** قراءة الـ ID المطلوب.
- **124:** البحث عن البروفايل داخل `studentProfiles`.
- **125-128:** لو الـ ID مش موجود، اطبع رسالة واخرج من الدالة.
- **130-131 - VULN-3:** بعد العثور على البروفايل، يتم عرضه مباشرة. لا يوجد شرط يقارن `profile.getOwnerUsername()` مع `currentUser.getUsername()`. لذلك Alice تقدر تطلب ID الخاص بـ Bob وتقرأ بياناته. ده IDOR / Broken Access Control.

### الأسطر 134-150: البحث داخل الـ LinkedList

- **134-141:** `findUser()` تمر على كل حساب بالترتيب. لو الاسم متطابق ترجع الحساب، ولو خلصت القائمة بدون تطابق ترجع `null`.
- **143-150:** `findStudentById()` تعمل نفس الفكرة لكن على بروفايلات الطلبة ومقارنة الـ ID.
- لأن البحث بيمر على العناصر واحدًا واحدًا، وقت البحث `O(n)`. ده مناسب لقائمة صغيرة في مشروع جامعي، وسبب استخدام `LinkedList` هنا هو متطلب التكليف.

### الأسطر 152-159: مساعدة المدخلات

- **152-154:** `hasStrongPassword()` تطبق سياسة كلمة السر باستخدام Regex. `(?=.*[a-z])` يطلب حرفًا صغيرًا، و`(?=.*[A-Z])` يطلب حرفًا كبيرًا، و`(?=.*\d)` يطلب رقمًا، والجزء `(?=.*[^a-zA-Z0-9])` يطلب رمزًا؛ ثم `.{10,}` يفرض 10 أحرف على الأقل.
- **156-159:** `readLine()` تطبع السؤال وتعيد السطر الذي أدخله المستخدم بدل تكرار `System.out.print()` و`scanner.nextLine()` في كل مكان.
- **160:** نهاية الكلاس.

## 5. بالضبط إيه اللي اتغير في النسخة الآمنة؟

### إصلاح VULN-1: إزالة بيانات الدخول الثابتة

في `src-secure/StudentPortalApp.java`، `authenticate()` لا تقارن بأي كلمة سر مكتوبة في المصدر ولا تنشئ Admin session خاصًا. لازم الحساب يكون مسجلًا في قائمة المستخدمين.

### إصلاح VULN-2: التحقق الفعلي من كلمة السر

الشرط الآمن هو:

```java
if (account == null || !account.passwordMatches(password)) {
    return null;
}
```

`||` معناها OR: ارفض لو الحساب غير موجود **أو** كلمة السر غير صحيحة. و`passwordMatches()` تستدعي تحقق PBKDF2.

### إصلاح VULN-3: التحقق من ملكية البروفايل

بعد ما نتأكد إن البروفايل موجود، وقبل عرضه، النسخة الآمنة تنفذ:

```java
if (!profile.getOwnerUsername().equals(currentUser.getUsername())) {
    System.out.println("Access denied. You can only view your own profile.");
    return;
}
```

لو مالك البيانات مختلف عن المستخدم الحالي، نوقف التنفيذ قبل طباعة أي بيانات من البروفايل.

## 6. الاختبارات خطوة بخطوة

1. شغّل `src-vulnerable` وسجّل Alice بكلمة السر `Alice@2026!` وبياناتها `Alice Example` / `Computer Science`؛ هتحصل على `S1001`.
2. سجّل Bob بكلمة السر `Bob@2026!!` وبياناته `Bob Example` / `Cyber Security`؛ هياخد `S1002`.
3. جرّب `admin` / `Admin@123` في النسخة الضعيفة؛ الدخول لازم ينجح. في النسخة الآمنة، نفس الدخول لازم يفشل.
4. جرّب الدخول باسم `alice` وكلمة سر `wrong-password`: النسخة الضعيفة تقبل الدخول بسبب VULN-2، والآمنة ترفض.
5. لتجربة IDOR بشكل منفصل، ادخل Alice بكلمة السر الصحيحة `Alice@2026!` واطلب `S1002`. النسخة الضعيفة تعرض Bob؛ النسخة الآمنة ترفض.
6. لتصوير دليل واضح، خذ Screenshot من الكود الضعيف، ثم Screenshot من نتيجة الاختبار، وبعدها صوّر الإصلاح والنتيجة الآمنة.

## 7. ملاحظات أمان مهمة

- كلمة السر في الحساب المسجل لا تتخزن كنص صريح؛ تخزن PBKDF2 hash مع salt.
- حسابات وبروفايلات الطلاب موجودة في الذاكرة، فبتختفي عند إغلاق البرنامج. ده مشروع تعليمي وليس نظامًا جامعيًا إنتاجيًا.
- لا تستخدم بيانات دخول التدريب في أي تطبيق حقيقي.
- **Static Analysis** يراجع المصدر من غير تشغيل، **Symbolic Execution** يحلل الشروط والمسارات منطقيًا، و**Debugging** يتابع قيم المتغيرات أثناء التنفيذ. دي تقنيات التحليل الموجودة في الصورة، أما الـ vulnerabilities فهي الأنواع الثلاثة المذكورة فوق.
